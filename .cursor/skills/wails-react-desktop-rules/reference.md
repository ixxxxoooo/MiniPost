# 详细参考规则

## 1. 产品目标

这是一个 macOS 优先的轻量级桌面 HTTP 调试工具，不是网页后台，也不是臃肿平台。
任何设计和实现都必须优先考虑：

- 轻量
- 快
- 清晰
- 原生感
- 可维护

## 2. 技术约束

- Backend: Go
- Desktop container: Wails
- Frontend: React + TypeScript
- Styling: Tailwind CSS
- Components: shadcn/ui
- State: 简洁稳定，不要过度引入复杂依赖
- 所有代码必须强类型
- 不允许无意义抽象

## 3. Wails 规则

- Go 层负责系统能力、网络请求、文件持久化、运行时能力
- React 层只负责 UI 和前端状态
- 不要让前端直接处理底层文件系统细节
- 所有前后端通信通过明确的 service / binding API
- Binding 返回值必须结构化，避免随意返回 any
- 所有错误必须统一格式返回
- 所有 IO 操作必须可恢复、可提示、可记录日志
- 请求发送逻辑优先放在 Go 层，避免浏览器环境限制影响 HTTP 调试能力
- 设计时考虑未来支持代理、证书、cookie jar、导入导出扩展

## 4. 架构规则

- 优先模块化，不要大而全单文件
- 按 domain / feature 分层
- 组件分为：基础 UI 组件、业务组件、布局组件
- 类型定义集中管理
- API DTO 与 ViewModel 分离
- Store 中不要塞过多派生逻辑
- 复杂逻辑提取为 hooks 或 service
- 所有列表、树、表单都必须有可复用抽象，但不要过度抽象

## 5. UI 规则

- 风格偏 macOS desktop
- 少即是多
- 边框轻、阴影轻、颜色克制
- 以灰阶和层次为主，品牌色只做点缀
- 间距统一，字号统一，圆角统一
- 优先 split view、sidebar、toolbar 的桌面布局
- 尽量避免明显“网页感”
- 支持 light / dark / system
- 优先键盘可操作性
- 焦点态、hover 态、active 态必须明确但不夸张

## 6. 交互规则

- 常用操作必须少点击
- 请求编辑和响应查看要尽量在同一主工作区完成
- 所有 destructive 操作都要二次确认
- 所有耗时操作显示 loading
- 所有失败操作显示明确错误信息
- 表单变更需要 dirty 状态提示
- 关闭前若未保存，要提示用户
- 支持快捷键：
  - Cmd+N 新建请求
  - Cmd+S 保存
  - Cmd+Enter 发送请求
  - Cmd+K 打开命令面板（预留）
  - Cmd+, 打开设置

## 7. 代码风格规则

- 不写 any，除非有明确理由
- 所有函数名语义明确
- 尽量使用纯函数
- 避免超长组件
- 单个组件超过 250 行要考虑拆分
- 单个文件职责单一
- 枚举、常量、schema、类型集中定义
- UI 状态和业务状态分离
- 统一错误处理和日志处理
- 写代码时附带必要注释，但不要废话注释

## 8. 数据与持久化规则

- 本地持久化结构清晰，版本可迁移
- 数据格式必须可扩展
- 导出 JSON 时保留 schemaVersion
- Secret 字段要有脱敏策略
- 删除操作优先软删除或可恢复（如果实现成本低）
- 历史记录有上限，避免无限膨胀

## 9. 响应渲染规则

- JSON 响应自动格式化
- 大响应要考虑性能
- 二进制响应不要强行按文本渲染
- HTML / 图片尽量支持预览
- 错误响应尽量识别 problem+json
- 响应区必须展示：
  - 状态码
  - 耗时
  - 大小
  - headers
  - body

## 10. 可扩展性规则

架构必须为以下能力预留空间，但第一版不强制实现：

- cURL import
- Postman Collection import/export
- OpenAPI import
- OAuth 2.0
- Pre-request scripts
- Tests
- Proxy
- SSL certificates
- Cookie manager
- 多标签页
- 多窗口（如果后续切换更高版本 Wails）

## 11. 输出要求

每次输出代码时：

1. 先说明本次实现的模块目标
2. 再说明会新增或修改哪些文件
3. 然后输出完整代码
4. 最后给出如何接入和验证

补充要求：

- 不要只给片段，尽量给可直接落地的代码
- 不要省略关键类型定义和依赖说明
- 输出方案时优先考虑生产可维护性，而不是一次性堆功能
